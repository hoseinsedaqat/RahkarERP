# راهکار | ERP Platform

یک ERP ماژولار با TypeScript در frontend و backend. این نسخه، پایه‌ی محصول و داشبورد عملیاتی را فراهم می‌کند تا ماژول‌ها به‌صورت تدریجی و قابل استفاده ساخته شوند.

## آخرین تغییرات (فاز داشبورد پویا و لندینگ جدید)

- **داشبورد واقعاً پویا**: همه KPIها از داده‌های زنده محاسبه می‌شوند (مانده نقدینگی، فروش، مطالبات، سفارش‌های باز)،
  «کارهای من» از رکوردهای هر ماژول ساخته می‌شود و تأیید هر مورد، داشبورد و کارتابل همان ماژول را به‌روزرسانی می‌کند.
- **رفع ایراد اصلی ثبت رویداد**: فرم «ثبت رویداد جدید» پیش‌تر هندلر ذخیره نداشت و رکوردی ثبت نمی‌شد؛ اکنون ثبت،
  تأیید و حذف در کارتابلِ همه ماژول‌ها (حتی ماژول‌های تخصصی) اثر فوری دارد.
- **کارتابل مشترک** زیر صفحه‌ی هر ماژول + نمودار توزیع رویدادها و دسترسی سریع به ۱۶ ماژول.
- **صفحه لندینگ کامل ۲۰۲۶**: هدر چسبان، هیرو با پس‌زمینه‌ی متحرک، ویژگی‌های محصول، ویترین ۱۶ ماژول،
  ۳ پلن قیمت با سوییچ ماهانه/سالانه، بخش ارتباط با ما (فرم + اطلاعات تماس) و فوتر.
- **بهبود صفحه ورود**: نمایش/پنهان‌سازی رمز، بازگشت به صفحه اصلی، حالت بارگذاری هنگام ورود و پس‌زمینه‌ی متحرک.
- **ماژول‌های بودجه، CRM و گزارش‌گیری بازطراحی شدند**: داده‌محور با افزودن/حذف سرنخ، تیکت و ردیف بودجه،
  تغییر وضعیت تیکت و خروجی CSV واقعی برای Excel (تراز آزمایشی، فروش، خزانه، موجودی، حقوق و رویدادها).

## نسخه وب (انتشار روی GitHub Pages)

آدرس منتشرشده:

نسخه‌ی منتشرشده روی Pages **بدون سرور** است؛ با `npm run build:demo` ساخته می‌شود:

- هیچ درخواستِ شبکه‌ای ارسال نمی‌شود و هیچ خطای اتصالی دیده نمی‌شود،
- ورود با حساب‌های معرفی‌شده انجام می‌شود (`admin / admin123` و `hesabdari`, `foroosh`, `anbar` با `1234`)
  و هر نقش دقیقاً همان دسترسی‌های نسخه‌ی اصلی را دارد،
- مجموعه‌ای از داده‌های نمونه (اسناد حسابداری، فروش، خرید، خزانه، چک‌ها، انبار، حقوق)
  هنگامِ نخستین ورود بارگذاری می‌شود تا بازدیدکننده یک سیستمِ پُر و واقعی ببیند،
- همه‌ی داده‌ها فقط در مرورگرِ بازدیدکننده می‌مانند؛ نشانگرِ بالای صفحه «نسخه‌ی نمایشی» را نشان می‌دهد.

برای دیدنِ همین نسخه روی دستگاهِ خودتان:

```bash
npm run build:demo:local     # خروجی در پوشه‌ی dist-demo
node scripts/serve-static.mjs dist-demo 8081
```

### روش انتشار

فایل `.github/workflows/deploy-pages.yml` آماده است و با هر push روی `main` (یا شاخه‌های `arena/**`)
خروجی را می‌سازد و روی Pages منتشر می‌کند؛ از تب Actions با `Run workflow` هم قابل اجراست.
برای فعال‌سازی، منبع Pages یک‌بار باید روی **GitHub Actions** تنظیم شود
(`Settings → Pages → Build and deployment → Source: GitHub Actions`).

> نکته: پوشه‌ی `docs/` جای مستنداتِ فارسیِ پروژه است؛ به همین دلیل خروجیِ انتشار
> در پوشه‌ی `dist` ساخته می‌شود (و شامل `.nojekyll` و `404.html` است).

در حالت Pages چون backendای در کار نیست، اپلیکیشن به‌طور خودکار روی **حالت نمایشی/محلی**
کار می‌کند و نشانگرِ وضعیت در نوار بالا این موضوع را نشان می‌دهد.

## اجرا

پیش‌نیاز: Node.js **20.19+** یا **22.12+** (نسخه‌های ۲۳ و ۲۴ هم پشتیبانی می‌شوند)

> راهنمای کامل و قدم‌به‌قدمِ ویندوز ۱۱ (حالت سرور، سرویس دائمی، رفع اشکال): [`docs/راهنما-اجرا-ویندوز.md`](docs/راهنما-اجرا-ویندوز.md)

### حالت سرور (توصیه‌شده برای استفاده‌ی واقعی) — یک فرآیند روی پورت ۸۰۸۰

```bash
npm install
cp .env.example .env      # ویندوز: copy .env.example .env
npm start                 # ساخت خروجی + بالا آوردن سرور روی http://localhost:8080
```

روی ویندوز می‌توانید به‌جای دستور بالا روی `scripts\windows\راه‌اندازی-ویندوز.bat` دوبار کلیک کنید.

ورود پیش‌فرض: `admin / admin123`

### حالت توسعه (Vite + API جداگانه)

```bash
npm install
npm run dev
```

- frontend: http://localhost:5173 (درخواست‌های `/api` به‌طور خودکار به backend پروکسی می‌شوند)
- API: http://localhost:4000/api/health

برای اجرای تک‌فرآیندی (frontend ساخته‌شده + API روی یک پورت):

```bash
npm run build
npm start          # معادل build + سرور
# یا فقط سرور (بدون ساخت دوباره): npm run serve
```

### متغیرهای محیطی

فایل `.env.example` را به `.env` کپی کنید. مهم‌ترین‌ها: `PORT` (پیش‌فرض ۴۰۰۰ برای توسعه، ۸۰۸۰ برای سرور)،
`NODE_ENV=production` و `JWT_SECRET` (اختیاری؛ در نبودش سرور خودش یک کلیدِ پایدار در `.data/` می‌سازد).

برای ساخت خروجی انتشار (GitHub Pages) در پوشه‌ی `docs/`:

```bash
npm run build:pages
```

وابستگی‌ها نصب شده‌اند و build تولیدی با موفقیت اجرا می‌شود.

## متغیرهای محیطی

فایل `.env.example` را به `.env` کپی و مقادیر را تنظیم کنید:

| متغیر | کاربرد | پیش‌فرض |
| --- | --- | --- |
| `DATABASE_URL` | اتصال PostgreSQL؛ در نبود آن سرور با کاربر demo اجرا می‌شود | خالی |
| `PORT` | پورت سرور وب/API | `4000` |
| `CORS_ORIGIN` | مبدأ مجاز برای CORS (احراز هویت توکنی است، نه کوکی) | `*` |
| `SERVE_STATIC` | سرو فایل‌های `dist` توسط همان سرور Node | خودکار در صورت وجود `dist` |
| `VITE_API_BASE` | آدرس backend در سمت مرورگر (خالی = همان دامنه) | خالی |
| `BASE_PATH` | مسیر انتشار استاتیک برای زیرمسیرها | `./` (نسبی) |
| `API_TARGET` | آدرس backend برای پروکسی در حالت توسعه | `http://localhost:4000` |

## ساختار

```text
src/main.ts            داشبورد و تعاملات frontend
src/styles.css         طراحی RTL و responsive
src/login-modern.css   طراحی صفحه ورود
server/index.ts        سرور وب: API + سرو خروجی استاتیک
server/database.ts     لایه دسترسی PostgreSQL
database/schema.sql    مدل PostgreSQL برای هسته ERP
vite.config.ts         تنظیمات build، پروکسی /api و base نسبی
docs/                  خروجی ساخته‌شده برای انتشار روی GitHub Pages
.env.example           نمونه متغیرهای محیطی
```

فایل `server/node-shim.d.ts` (تعریف دستی و ناقص تایپ‌های `node:http`) حذف شد؛
تایپ‌های رسمی `@types/node` جایگزین آن هستند و `tsc --noEmit` بدون خطا اجرا می‌شود.
همچنین خروجی `dist/` دیگر در git نگه‌داری نمی‌شود (`.gitignore`) و در CI یا با
`npm run build` ساخته می‌شود.

## وضعیت فعلی

- داشبورد نمای کلی سازمان
- registry قابل توسعه برای ۱۶ دامنه: هویت، سازمان، گردش کار، یکپارچه‌سازی، مالی، خزانه، فروش، خرید، انبار، حقوق، منابع انسانی، دارایی ثابت، تولید، بودجه، CRM و BI
- صفحه پویا برای هر دامنه با KPI و تمام زیرقابلیت‌های درخواست‌شده
- endpointهای `/api/modules` و `/api/modules/:id` برای قرارداد backend
- جست‌وجوی رویدادها
- ثبت رویداد جدید با وضعیت انتظار بررسی و اتصال مفهومی به پل حسابداری
- فرم واقعی برای تمام زیرقابلیت‌ها، ذخیره‌ی ماندگار روی سرور (`/api/workspace`) و ارسال به APIهای تخصصی
- کارتابل هر ماژول با تأیید و حذف رکوردهای ثبت‌شده
- seed آموزشی برای آشنایی کاربر جدید با جریان‌های مالی، فروش، خرید، انبار، منابع انسانی و تولید
- workspace تخصصی مالی با سند چندردیفی بدهکار/بستانکار، کنترل تراز لحظه‌ای و دو سند نمونه
- endpoint ثبت سند حسابداری: `POST /api/accounting/journals`
- گزارش تراز آزمایشی و دفتر کل از روی اسناد ثبت‌شده
- endpoint گزارش مانده حساب‌ها: `GET /api/accounting/balances`
- workspace عملیاتی خزانه‌داری با KPI مانده خالص، دریافت، پرداخت و دفتر تراکنش
- endpointهای خزانه‌داری: `GET/POST /api/treasury`
- پل حسابداری خزانه: دریافت = بدهکار بانک/صندوق و بستانکار دریافتنی؛ پرداخت = بدهکار بدهی و بستانکار بانک/صندوق
- workspace عملیاتی فروش با فاکتور چندقلمی، تخفیف، مالیات و اتصال خودکار به درآمد/دریافتنی
- endpointهای فروش: `GET/POST /api/sales/invoices`
- workspace منابع انسانی و حقوق با کارکنان نمونه، اضافه‌کاری، کسورات و فیش حقوقی
- endpoint کارکنان: `GET /api/hr/employees`
- endpoint محاسبه حقوق: `POST /api/payroll/runs`
- endpoint ثبت و فهرست رویدادها: `GET/POST /api/events`
- کارت‌های KPI و فهرست کارهای کاربر
- endpoint سلامت backend
- ورود آزمایشی با `admin / admin123` و نشست ماندگار مرورگر
- خروج از نشست و نمایش سازمان، نقش و کاربر فعال
- احراز هویت API در `/api/auth/login` با hash رمز عبور `scrypt`
- اتصال اختیاری PostgreSQL از طریق `DATABASE_URL` و اجرای خودکار schema هنگام شروع server
- schema اولیه برای سازمان، کاربران، نقش‌ها، مجوزها، گردش کار، حسابداری، رویداد دامنه و audit log

## نکته مهم

این مرحله یک prototype عملیاتی با هسته‌ی آماده‌ی مهاجرت است، نه ERP آماده‌ی بهره‌برداری سازمانی. API فعلاً حافظه‌ای است و frontend برای کار بدون سرور localStorage دارد. schema PostgreSQL در `database/schema.sql` آماده شده، اما repository، hash رمز عبور، مجوز واقعی endpointها و migration runner باید پیش از production تکمیل شوند.

برای persistence واقعی، مقدار `DATABASE_URL` را مطابق `.env.example` در فایل `.env` تنظیم کنید. در نبود آن، server در حالت توسعه با کاربر demo و storage موقت اجرا می‌شود.

داده‌های نمونه فقط زمانی ساخته می‌شوند که کارتابل مرورگر خالی باشد و با برچسب «داده نمونه آموزشی» مشخص هستند. کاربر می‌تواند برای هر زیرماژول رکورد جدید ثبت کند، آن را تأیید کند یا حذف نماید.

## ترتیب توسعه تک‌نفره

1. اجرای `database/schema.sql` روی PostgreSQL و جایگزینی storage حافظه‌ای با repository
2. مالی: حساب‌ها، اسناد دوطرفه، دفتر کل، طرف حساب و دوره مالی
3. خزانه: بانک، صندوق، دریافت، پرداخت و چک
4. فروش، خرید و انبار با رویدادهای مالی یکپارچه
5. گزارش‌ساز و داشبوردهای قابل فیلتر
6. منابع انسانی و حقوق و دستمزد با قوانین رسمی کشور
7. دارایی ثابت، تولید، CRM و BI

## اصل معماری

نسخه اول به شکل Modular Monolith توسعه داده می‌شود. هر ماژول باید مدل، سرویس، API و تست مستقل داشته باشد و برای ارتباط با دیگر ماژول‌ها از قراردادهای مشخص و رویدادهای دامنه استفاده کند. پس از اثبات نیاز و رشد بار، فقط بخش‌های لازم به سرویس مستقل تبدیل می‌شوند.

## فاز ۱ — هسته‌ی واقعی سیستم (ذخیره‌سازی، احراز هویت، دسترسی و ردیابی)

### ذخیره‌سازی ماندگار (`server/store.ts`)
بدون نیاز به هیچ دیتابیس خارجی، داده‌ها در فایل `.data/store.json` نگه‌داری می‌شوند:
نوشتن‌ها اتمیک (فایل موقت + تغییر نام) و پشت یک صف انجام می‌شوند، بنابراین بعد از ری‌استارت سرور
هیچ داده‌ای از بین نمی‌رود. با تنظیم `DATABASE_URL` همان مسیرها به PostgreSQL منتقل می‌شوند.

### احراز هویت و نقش‌ها (`server/auth.ts`)
- رمز عبور با الگوریتم **scrypt** و نمک تصادفی و مقایسه‌ی زمان‌ثابت ذخیره می‌شود
- توکن ورود **JWT** با امضای HS256 و اعتبار ۸ ساعت (`JWT_SECRET` در محیط)
- پنج نقش با مدل RBAC: مدیر سیستم، حسابدار، کارشناس فروش، انباردار، ناظر

| نقش | نام کاربری | رمز عبور | تعداد دسترسی |
| --- | --- | --- | --- |
| مدیر سیستم | `admin` | `admin123` | ۱۶ |
| حسابدار | `hesabdari` | `1234` | ۹ |
| کارشناس فروش | `foroosh` | `1234` | ۵ |
| انباردار | `anbar` | `1234` | ۵ |

### ردیابی عملیات و شماره‌گذاری
هر عملیات حساس (ورود ناموفق، ثبت رویداد، ثبت سند، مدیریت کاربر، دریافت شماره سند)
با کاربر، زمان و توضیح ثبت می‌شود و از مسیر `GET /api/audit` (فقط نقش مدیر) در
ماژول «هویت و دسترسی» قابل مشاهده است. شماره‌گذاری اسناد با `POST /api/numbering/:key`
به‌صورت یکتا و ماندگار انجام می‌شود.

### endpointهای جدید
`POST /api/auth/login` · `GET /api/me` · `GET /api/audit` · `GET /api/stats` ·
`GET /api/numbering` · `POST /api/numbering/:key` · `POST /api/identity/users` · `DELETE /api/events?id=`

## فاز ۱ (۲) — سال مالی، مراکز هزینه و گردش کار چندمرحله‌ای

### موتور گردش کار (`server/workflow.ts`)
چرخه‌ی عمر هر سند در یک جدول انتقال تعریف شده است؛ تغییر فرآیند سازمان فقط با
ویرایش همین جدول انجام می‌شود:

```
پیش‌نویس ──submit──▶ ارسال‌شده ──review──▶ بررسی‌شده ──approve──▶ تأیید‌شده ──post──▶ قطعی
                          │                     │                     │
                       reject                return                reject
                          ▼                     │                     ▼
                        ردشده ◀─────────────────┘                  ردشده
```

هر انتقال دسترسی لازم را مشخص می‌کند (مثلاً `approve` فقط برای نقش‌های دارای
`accounting.write`) و هر تغییر با کاربر، زمان و توضیح در تاریخچه‌ی سند ثبت می‌شود.

### سال مالی و مراکز هزینه
- ۱۲ دوره‌ی ماهانه برای سال ۱۴۰۵ به‌صورت خودکار ساخته می‌شود (باز/بسته‌کردن هر دوره)
- مراکز هزینه‌ی پایه برای تخصیص هزینه و بودجه
- هر سند می‌تواند به یک دوره و یک مرکز هزینه متصل شود

### در رابط کاربری
- «کارهای من» اسناد سرور را هم نشان می‌دهد؛ هر سند نشان وضعیت و دکمه‌های انتقال مجاز دارد
- زیر کارتابل هر ماژول، اسنادِ همان ماژول با دکمه‌ی تاریخچه (⋯) نمایش داده می‌شوند
- ماژول حسابداری پنل «سال مالی و مراکز هزینه» دارد (بستن/بازگشایی دوره، افزودن مرکز هزینه)

### endpointهای جدید
`GET/POST /api/documents` · `GET /api/documents/:id` · `POST /api/documents/:id/transitions` ·
`GET /api/documents/transitions` · `GET/POST /api/fiscal-periods` · `PATCH /api/fiscal-periods/:id` ·
`GET/POST /api/cost-centers`

## فاز ۱ (۳) — مهاجرت‌های پایگاه داده

ساختار پایگاه در قالب مهاجرت‌های نسخه‌دار نگه‌داری می‌شود:

```
database/migrations/
  001_initial_schema.sql        ساختار پایه (۲۸ جدول)
  002_workflow_and_centers.sql  اسناد، تاریخچه گردش کار، مراکز هزینه و تکمیل دوره‌های مالی
```

اجرا:

```bash
npm run migrate                                    # اجرای آزمایشی روی PostgreSQL درون‌حافظه (بدون نیاز به سرور)
DATABASE_URL=postgres://... npm run migrate        # اجرا روی پایگاه واقعی
```

ویژگی‌ها:
- هر مهاجرت در یک تراکنش اجرا و همراه با **اثر انگشت فایل** در جدول `schema_migrations` ثبت می‌شود
- اجرای دوباره بی‌اثر است و رکورد تکراری نمی‌سازد (تست‌شده)
- سرور هنگام بالا آمدن، مهاجرت‌های اجرانشده را خودکار اعمال می‌کند
- داده‌های پایه (سازمان، کاربران، نقش‌ها و دسترسی‌ها، حساب‌ها، دوره‌های مالی، مراکز هزینه)
  به‌صورت تکرارپذیر توسط `server/seed.ts` درج می‌شوند

## فاز ۲ (۱) — موتور صدور سند حسابداری

هر عملیات مالی با یک «قاعده» به سند حسابداری استاندارد و **همیشه متوازن** تبدیل می‌شود
(`server/accounting-engine.ts`):

| عملیات | بدهکار | بستانکار |
| --- | --- | --- |
| فروش | دریافتنی ۱۲۰۰ | درآمد ۴۰۰۰ + ارزش افزوده ۲۲۰۰ |
| خرید | موجودی ۱۳۰۰ + ارزش افزوده ۲۲۰۰ | پرداختنی ۲۰۰۰ |
| حقوق و دستمزد | هزینه حقوق ۶۱۰۰ | حقوق پرداختنی ۲۱۰۰ |
| دریافت نقدی | بانک ۱۱۰۰ | دریافتنی ۱۲۰۰ |
| پرداخت نقدی | پرداختنی ۲۰۰۰ | بانک ۱۱۰۰ |
| استهلاک | هزینه استهلاک ۶۲۰۰ | استهلاک انباشته ۱۵۰۱ |
| تولید | کالای در جریان ساخت ۱۴۰۰ | موجودی مواد ۱۳۰۰ |

- **صدور خودکار**: وقتی سندی در گردش کار به وضعیت «قطعی» می‌رسد، سند حسابداری آن
  بلافاصله و به‌صورت قطعی صادر می‌شود و شماره‌اش در پیام对用户 نمایش داده می‌شود
- **تضمین توازن**: هر سند پیش از ذخیره بررسی می‌شود (جمع بدهکار = جمع بستانکار) و
  تراز آزمایشی همواره جمع صفر دارد
- **دفتر روزنامه و تراز آزمایشی**: در ماژول حسابداری، اسناد صادرشده با امکان
  مشاهده‌ی سطرها و قطعی‌کردن، به همراه خلاصه‌ی وضعیت مالی

### endpointهای جدید
`GET/POST /api/accounting/entries` · `POST /api/accounting/entries/:id/post` ·
`GET /api/accounting/trial-balance` · `GET /api/accounting/summary`

## امنیت نشست و نمایش نقش واقعی

- کارت کاربر در نوار کناری از **نشست واقعی** خوانده می‌شود (پیش‌تر مقدار ثابت «مدیر سیستم» نمایش داده می‌شد)
- هر نقش تنها بخش‌های مجاز را می‌بیند و در صورت نبود دسترسی، پیام شفاف نمایش داده می‌شود
- نشست سرور هنگام بارگذاری برنامه بررسی می‌شود؛ اگر سرور نشستِ ذخیره‌شده را نپذیرد
  (کلیدِ امضا عوض شده، پوشه‌ی `.data` پاک شده یا نشست منقضی شده)، نشانه‌های کهنه پاک
  و **صفحه‌ی ورود** نمایش داده می‌شود. «حالت محلی» دیگر وجود ندارد: هیچ ثبتی بدون نشستِ
  معتبرِ سرور انجام نمی‌شود
- بدون سرور ورودی انجام نمی‌شود و پیامِ شفاف «ارتباط با سرور برقرار نشد» نشان داده می‌شود


## فاز ۲ (۲) — گزارش‌های مالی، تطبیق بانکی و بهای تمام‌شده

### گزارش‌های مالی (محاسبه از اسناد قطعی)

| گزارش | توضیح |
| --- | --- |
| **ترازنامه** | دارایی‌ها = بدهی‌ها + حقوق صاحب سرمایه (شامل سود/زیان دوره با علامت) |
| **سود و زیان** | درآمدها − هزینه‌ها با نمایش سود یا زیان خالص |
| **دفتر کل** | گردش بدهکار/بستانکار و مانده‌ی هر حساب |
| **دفتر معین** | گردش یک حساب با مانده‌ی روندی و تفکیک مرکز هزینه |
| **اظهارنامه ارزش افزوده** | مالیات خروجی (فروش) − ورودی (خرید) = قابل پرداخت |

همه‌ی گزارش‌ها فقط از **اسناد قطعی‌شده** محاسبه می‌شوند و امکان فیلتر بازه‌ی تاریخ دارند.

### تطبیق بانکی

- ثبت ردیف‌های صورت‌حساب بانک (دریافت/پرداخت)
- مقایسه‌ی خودکار با سطرهای حساب بانک (۱۱۰۰) در اسناد قطعی
- پیشنهاد تطبیق بر اساس **برابری مبلغ** و **نزدیکی تاریخ** با درصد اطمینان
- تطبیق دستی و لغو تطبیق؛ هر سطر دفتر فقط یک‌بار تطبیق می‌خورد

### بهای تمام‌شده‌ی موجودی

- دو روش **میانگین موزون (WAC)** و **FIFO**
- ثبت ورود (با بهای واحد) و خروج (بهای واحد به‌طور خودکار بر اساس روش انتخابی)
- جلوگیری از خروج بیش از موجودی
- مقایسه‌ی ارزش موجودی در دو روش

### تفکیک داده‌ها بر اساس کاربر

داده‌های ماژول‌ها (فاکتور، سفارش، کالا، کارمند، سرنخ، بودجه و …) برای هر شرکت روی
سرور نگه داشته می‌شود (`GET/PUT /api/workspace` → `.data/store.json` → بخشِ `workspaces`).
مرورگر فقط یک نسخه‌ی موقت (کش) دارد که با هر ورود از سرور بازنویسی می‌شود؛ پاک شدنِ
حافظه‌ی مرورگر هیچ داده‌ای را از بین نمی‌برد و هر مرورگرِ دیگری همان داده‌ها را می‌بیند.
با تغییر کاربر یا شرکت، داده‌ها، کارتابل و گزارش‌های همان شرکت نمایش داده می‌شود. کاربرانی که
دسترسی ندارند، به‌جای صفحه‌ی خالی پیام «عدم دسترسی» می‌بینند.

### endpointهای جدید
`GET /api/accounting/balance-sheet` · `GET /api/accounting/profit-loss` ·
`GET /api/accounting/general-ledger` · `GET /api/accounting/subsidiary?account=` ·
`GET /api/accounting/vat` · `GET|POST /api/inventory/movements` ·
`GET /api/inventory/costing?method=wac|fifo` · `GET|POST /api/treasury/statements` ·
`GET|POST /api/treasury/reconciliation`


## اصلاحات محاسباتی گزارش‌ها

- جهت مانده‌ی حساب‌ها (بدهکار/بستانکار) بر اساس طبیعت حساب تعیین می‌شود
- استهلاک انباشته در ترازنامه با علامت منفی و در دفتر کل با عنوان «بستانکار» نمایش داده می‌شود
- ترازنامه همیشه با معادله‌ی «دارایی‌ها = بدهی‌ها + حقوق صاحب سرمایه» بررسی و اعلام می‌شود
- مالیات بر ارزش افزوده با نرخ ۹٪ (مبلغ شامل مالیات) هنگام صدور خودکار فروش و خرید اعمال می‌شود


## فاز ۳ — حقوق و دستمزد ایران و چک‌ها

### محاسبه حقوق طبق قانون کار

| مورد | محاسبه |
| --- | --- |
| مزایای قانونی | حق مسکن + خواربار + حق اولاد (به‌ازای هر فرزند) + پایه سنوات |
| بیمه | سهم کارمند ۷٪ و سهم کارفرما ۲۳٪ از مبلغ مشمول |
| مالیات حقوق | پلکانی با معافیت ماهانه و نرخ‌های قابل تنظیم |
| عیدی | مزد روزانه × ۶۰ روز، با سقف ۹۰ روز حداقل مزد |
| سنوات | یک ماه حقوق به‌ازای هر سال خدمت |
| خالص پرداختی | ناخالص − بیمه کارمند − مالیات − کسورات |

تمام نرخ‌ها و سقف‌ها در `server/payroll-engine.ts` به‌صورت **پارامتر قابل تنظیم** تعریف شده‌اند
تا با بخشنامه مزد و قانون بودجه هر سال به‌روزرسانی شوند.

ثبت هر فیش می‌تواند به‌طور خودکار **سند حسابداری حقوق** صادر کند.

### مدیریت چک‌ها

- چک‌های دریافتنی و پرداختنی با شماره، سریال، بانک و سررسید
- وضعیت‌ها: در جریان وصول، وصول شده، پرداخت شده، برگشتی، باطل شده
- هشدار سررسید یک هفته آینده و خلاصه مبالغ

## فاز ۳ (ادامه) — دارایی، تولید و رهگیری کالا

### استهلاک خودکار دارایی‌ها

- سه روش استاندارد: **خط مستقیم**، **نزولی** و **مجموع سنوات**
- محاسبه‌ی زمان‌بندی کامل تا پایان عمر مفید و نمایش مانده‌ی ماه‌های باقیمانده
- محاسبه‌ی خودکارِ سقف استهلاک (هرگز از بهای قابل استهلاک عبور نمی‌کند)
- صدور **سند استهلاک دوره** (بدهکار ۶۲۰۰ هزینه استهلاک / بستانکار ۱۵۰۱ استهلاک انباشته)
  و به‌روزرسانی استهلاک انباشته‌ی هر دارایی
- محاسبه به‌صورت سروری و در نبود سرور به‌صورت محلی (حالت آفلاین)

### BOM و بهای تمام‌شده تولید

- تعریف **صورت مواد (BOM)**: محصول، خروجی هر دوره، مواد/قطعات با مقدار و ضایعات
- محاسبه‌ی **بهای تمام‌شده**: مواد مستقیم + دستمزد مستقیم + سربار (ثابت هر واحد
  و نرخ دقیقه‌ای) و در صورت نیاز درصد ضایعات سراسری
- نمایش **انحراف از بهای استاندارد** (مبلغ و درصد)
- ثبت سفارش تولید و صدور سند انتقال به **کالای در جریان ساخت (۱۴۰۰)**

### رهگیری شماره سریال کالا

- ثبت **گروهی** سریال با پیشوند، شمارنده و تعداد ارقام (تکراری‌ها نادیده گرفته می‌شوند)
- پنج وضعیت چرخه‌ی عمر: موجود در انبار، تخصیص‌یافته، فروخته‌شده، برگشتی، اسقاط
- جست‌وجو و فیلتر بر اساس وضعیت و تغییر وضعیت تک‌کلیک

## فاز ۴ (ادامه) — گزارش‌ساز و تحلیل بودجه

### گزارش‌ساز دلخواه

- ۸ منبع دادهٔ واقعی: اسناد حسابداری، موجودی کالا، حقوق و دستمزد، چک‌ها،
  شماره سریال‌ها، صورت مواد، گردش کار و ردپای حسابرسی
- انتخاب ستون‌ها، **فیلترهای چندگانه** (برابر، شامل، بزرگ‌تر، کوچک‌تر، بازه)
- **گروه‌بندی** همراه با جمع‌بندی (جمع، تعداد، میانگین، کمینه، بیشینه)
- مرتب‌سازی، محدودیت تعداد ردیف، جمع کل در پانوشت
- خروجی **اکسل (CSV)** و **چاپ/PDF**

### تحلیل بودجه و انحراف

- مقایسه‌ی مصوب با عملکرد واقعی برای هر ردیف بودجه
- انحراف مبلغی و درصدی، درصد تحقق (نمایش میله‌ای) و وضعیت: مطلوب / هشدار / بحرانی
- **هشدارهای مدیریتی** برای ردیف‌های نزدیک یا عبور کرده از سقف بودجه
- خلاصه‌ی تجمیعی **بر اساس مرکز هزینه**
- امکان تطبیق خودکار عملکرد واقعی با مانده‌ی حساب‌های دفتر کل (`fromAccounts`)

### نشست پایدار

- **نشست ۳۰ روزه**: توکن تازه‌سازی ۳۰ روز اعتبار دارد و توکن دسترسی (۲۴ ساعته)
  پیش از پایان، بی‌صدا و بدون دخالت کاربر نو می‌شود
- بازیابی **خودکار** نشست هنگام بارگذاری برنامه و هنگام دریافت پاسخ ۴۰۱
- **مقاوم در برابر پروکسی‌ها**: توکن هم در هدر `Authorization`، هم در `X-Auth-Token` و هم
  در یک کوکی `HttpOnly` هم‌مبدأ فرستاده می‌شود؛ اگر پروکسی/CDN یا تونلی هدر
  `Authorization` را حذف کند (مثل برخی پیش‌نمایش‌های ابری)، اتصال قطع نمی‌شود
- نشانگر وضعیت در نوار بالا: «● متصل به سرور» / «نشست منقضی شده» / «حالت آفلاین»
  و پنجرهٔ جزئیات اتصال شامل نشانی سرور، کاربر، سازمان و نقش

## کنترل دسترسی و تجربه‌ی کاربری

- **پنهان‌سازی کامل بر اساس نقش**: هر ماژولی که کاربر مجوز آن را ندارد، در منوی
  کناری، کارت‌های داشبورد و بدنه‌ی برنامه به‌طور کامل پنهان می‌شود (هیچ پیام
  «دسترسی ندارید» نمایش داده نمی‌شود). نگاشت ماژول‌ها به مجوزها در
  `modulePermissions` در `src/main.ts` تعریف شده است.
  - انباردار: نمای کلی، گردش کار، خرید، انبار، تولید
  - حسابدار: مالی، خزانه، فروش، خرید، حقوق، دارایی، بودجه، CRM، گزارش‌گیری
  - فروش: نمای کلی، گردش کار، فروش، انبار، CRM
- **دکمه‌های پنجره**: «بستن» (خنثی و شیک)، «انصراف» (قرمز ملایم) و دکمه‌ی اصلی
  با سایز، شعاع و ارتفاع یکسان
- **یکنواختی فرم‌ها**: همه‌ی ورودی‌ها، انتخاب‌گرها و جعبه‌های متن در همه‌ی بخش‌ها
  ارتفاع، حاشیه، شعاع و حالتِ فوکوس یکسانی دارند
- **فاصله‌گذاری**: بخش‌های هر ماژول با فاصله‌ی یکنواخت (۲۲ پیکسل) از هم جدا می‌شوند

### صورت‌های مالی در ماژول حسابداری

- **ترازنامه** (دارایی‌ها / بدهی‌ها / حقوق صاحبان سهام) با نمایش تراز بودن
- **سود و زیان** (درآمدها / هزینه‌ها / سود خالص / حاشیه سود)
- **مالیات بر ارزش افزوده** (خروجی، ورودی، قابل پرداخت و تعداد ردیف‌های مشمول)
- همه بر اساس داده‌های واقعیِ سرور (`/api/accounting/balance-sheet`،
  `/api/accounting/profit-loss`، `/api/accounting/vat`)

### گزارش‌ساز: تطبیق هوشمند فارسی

فیلترهای متنی در گزارش‌ساز با **نرمال‌سازی فارسی** مقایسه می‌شوند: نیم‌فاصله،
تفاوت «ی» و «ک» عربی/فارسی، اعداد فارسی و فاصله‌های اضافه نادیده گرفته می‌شوند؛
بنابراین «پیش نویس»، «پیش‌نویس» و «پيشنويس» همگی یکسان یافت می‌شوند.

## بازطراحی رابط کاربری

- **صفحه ورود جدید**: دو ستونه با پنل برند، ورودی‌های دارای آیکون، نمایش رمز،
  و چهار دکمه «ورود سریع» برای حساب‌های نمونه
- **پنجره‌ها**: عریض‌تر و جادارتر، بدنه و پاورقی مجزا، و دکمه «انصراف» با رنگ قرمز
- **واکنش‌گرایی کامل**: نوار کناری به صورت کشویی در موبایل، جداول قابل پیمایش افقی،

## فاز ۵ (۱) — چندشرکتی، راهنمای راه‌اندازی و پشتیبان‌گیری

سامانه اکنون می‌تواند چند کسب‌وکارِ کاملاً مستقل را هم‌زمان مدیریت کند.

### ۱. چندشرکتی واقعی

- هر شرکت (سازمان) داده‌ی کاملاً مجزا دارد: اسناد حسابداری، گردش کار، چک‌ها، حقوق و دستمزد، سریال‌ها، فرمول‌های ساخت و حرکت‌های انبار.
- **شماره‌گذاری اسناد برای هر شرکت مستقل است** (شرکت دوم از شماره‌ی ۱۰۰۱ شروع می‌کند، نه ادامه‌ی شرکت اول).
- انتخاب شرکت از بالای نوار کناری («شرکت انتخاب‌شده») انجام می‌شود؛ با انتخاب هر شرکت، همه‌ی داده‌ها از نو بارگذاری می‌شود.
- داده‌های محلی (حالت آفلاین) نیز با کلیدِ سه‌بخشیِ «کاربر / شرکت / نام داده» تفکیک شده‌اند و داده‌های قدیمی به‌طور خودکار به شرکت پیش‌فرض منتقل می‌شوند.
- هر کاربر برای هر شرکت یک نقشِ اختصاصی دارد (مثلاً در یک شرکت حسابدار و در شرکت دیگر فقط مشاهده‌گر).

| `POST /api/organizations` | ایجاد شرکت (سازنده مدیر همان شرکت می‌شود) |
| `PATCH /api/organizations/:id` | ویرایش یا غیرفعال‌سازی شرکت |
| `POST /api/organizations/default` | تعیین شرکت پیش‌فرضِ کاربر |
| `GET/POST /api/organizations/:id/members` | مدیریت اعضا و نقش آن‌ها در شرکت |

شرکت فعال با هدر `X-Organization-Id` مشخص می‌شود؛ اگر ارسال نشود، شرکت پیش‌فرضِ کاربر استفاده می‌گردد.

### ۲. راهنمای راه‌اندازی پنج‌مرحله‌ای

پس از ایجاد شرکت، راهنما در پنج گام شرکت را آماده می‌کند:

1. **قالب کسب‌وکار**: فروشگاه، تولیدی کوچک، شرکت خدماتی یا پیمانکاری.
2. **سال مالی**: سال، ماه آغاز و بازه‌ی دوره.
3. **سرفصل‌های حسابداری**: ایجاد خودکارِ سرفصل‌های متناسب با قالب انتخابی (۱۵ تا ۱۹ سرفصل).
4. **کاربران**: افزودن همکاران با نقشِ مشخص در همان شرکت.
5. **پایان**: نمایش خلاصه و ورود به شرکت جدید.

### ۳. پشتیبان‌گیری و بازگردانی یک‌کلیکی

در ماژول «سازمان و ساختار شرکت» پنل «پشتیبان‌گیری و بازگردانی» (ویژه‌ی مدیر) قرار دارد:

- **دریافت نسخه‌ی پشتیبان**: یک فایل JSON از همه‌ی شرکت‌ها، اسناد، چک‌ها، حقوق و کاربران.
- **بازگردانی از فایل**: جایگزینی کامل داده‌ها پس از تأیید؛ پیش از بازگردانی یک نسخه‌ی امن (`store.json.before-restore-*`) در سرور نگه داشته می‌شود.

اگر اتصال به سرور برقرار نباشد، پشتیبانِ محلی از داده‌های مرورگر گرفته می‌شود.

### ۴. رفعِ پیام «باید وارد سیستم بشید»

پیامی که هنگام کلیک روی برخی دکمه‌ها دیده می‌شد، به **پایان‌یافتنِ نشست** (توکن نامعتبر یا منقضی) مربوط بود، نه به دکمه‌ی خاصی. اکنون:

- متن خطا روشن‌تر شده: «نشست شما پایان یافته است؛ لطفاً دوباره وارد شوید.»
- سامانه نخست با توکن تازه‌سازی، نشست را بی‌صدا برمی‌گرداند.
- اگر باز هم موفق نشود، پنجره‌ی ورود باز می‌شود و هیچ پیامِ خامِ سروری به کاربر نشان داده نمی‌شود.

همچنین علتِ اصلیِ «کلیک می‌کنم و هیچ اتفاقی نمی‌افتد» برطرف شد: پیام‌های راهنما (Toast) پیش از این درونِ قسمتی از صفحه بودند که با هر بازسازیِ صفحه پاک می‌شدند؛ اکنون به بدنه‌ی صفحه متصل‌اند و همیشه دیده می‌شوند.
