# راهنمای اتصال به پایگاه داده

این راهنما برای کسی نوشته شده که برنامه‌نویس نیست. قدم‌به‌قدم جلو بروید؛ هر مرحله
یک خروجیِ قابلِ بررسی دارد و اگر جایی ایراد داشت، بخشِ «خطاهای متداول» در پایان را
بخوانید.

---

## ۰) پیش از هر چیز: برنامه بدون پایگاه داده هم کار می‌کند

به‌طور پیش‌فرض، راهکار همه‌چیز را در یک فایلِ امن در پوشه‌ی `.data/store.json`
نگه می‌دارد؛ یعنی:

- نصبِ پایگاه داده لازم نیست،
- برنامه روی هر ویندوز/لینوکسی بالا می‌آید،
- با خروجیِ CSV و فایلِ پشتیبان قابلِ انتقال است.

**چه زمانی پایگاه داده لازم می‌شود؟**
وقتی چند نفر هم‌زمان کار می‌کنند، حجمِ داده زیاد می‌شود، یا می‌خواهید روی اینترنت
(سرور ابری) منتشر کنید. در این صورت بروید سراغِ PostgreSQL (یا Supabase که همان
PostgreSQL است اما مدیریت‌شده).

---

## ۱) اتصال به PostgreSQL (روی کامپیوترِ خودتان یا سرور)

### ۱.۱ نصب
- **ویندوز:** بسته‌ی نصبِ PostgreSQL را از [postgresql.org](https://www.postgresql.org/download/windows/)
  بگیرید. هنگامِ نصب یک رمز برای کاربرِ `postgres` انتخاب کنید و آن را یادداشت کنید.
- **pgAdmin** همراهِ نصب می‌آید. آن را باز کنید و مطمئن شوید سرور در حال اجرا است
  (روی سرور راست‌کلیک → `Connect`).

### ۱.۲ ساختن پایگاه داده
در pgAdmin: راست‌کلیک روی **Databases → Create → Database**
- نام: `erp`
- Owner: `postgres`
- دکمه‌ی Save.

### ۱.۳ تنظیم در `.env`
فایلِ `.env.example` را کپی کنید و نامش را `.env` بگذارید، سپس این خط را ویرایش کنید:

```env
DATABASE_URL=postgres://postgres:YOUR_PASSWORD@localhost:5432/erp
```

- `YOUR_PASSWORD` همان رمزی است که هنگام نصب انتخاب کردید.
- اگر پایگاه روی دستگاهِ دیگری است، `localhost` را با آدرسِ IP آن عوض کنید.

### ۱.۴ ساختِ جداول (مهاجرت)
یک‌بار این دستور را اجرا کنید:

```bash
npm install
npm run migrate
```

خروجیِ موفق یعنی جداول ساخته شدند. در pgAdmin می‌توانید آن‌ها را ببینید:
`erp → Schemas → public → Tables`.

### ۱.۵ اجرا
```bash
npm start
```

از این لحظه داده‌ها در PostgreSQL ذخیره می‌شوند.

## ۲) اتصال به Supabase (برای انتشارِ آنلاین و کار با اینترنت)

Supabase همان PostgreSQL است، اما آماده و با پنلِ مدیریت در اینترنت.
مزیتش این است که نیازی به نصب و نگهداریِ پایگاه داده ندارید.

### ۲.۱ ساخت پروژه
1. به [supabase.com](https://supabase.com) بروید و یک حساب بسازید.
2. دکمه‌ی **New project** را بزنید؛ نام، رمزِ پایگاه داده و منطقه (نزدیک‌ترین
   منطقه به کاربران‌تان، مثلاً `Frankfurt`) را انتخاب کنید.
3. چند دقیقه صبر کنید تا پروژه آماده شود.

### ۲.۲ گرفتن رشته‌ی اتصال
در پنلِ پروژه: **Project Settings → Database → Connection string → URI**
یک رشته می‌بینید شبیه این:

```
postgres://postgres.abcdefgh:YOUR-PASSWORD@aws-0-eu-central-1.pooler.supabase.com:6543/postgres
```

⚠️ **نکته‌ی مهم:** اگر پورت `6543` بود (Transaction pooler)، آن را به **Session pooler**
تغییر دهید (در همان صفحه تبِ `Session pooler` را انتخاب کنید؛ پورت معمولاً `5432`).
برنامه از تراکنش‌های چندمرحله‌ای استفاده می‌کند و به اتصالِ Session نیاز دارد.

همچنین اگر از اینترنتِ شرکتی متصل می‌شوید و خطای SSL گرفتید، این را به انتهای رشته اضافه کنید:

```
?sslmode=require
```

### ۲.۳ تنظیم در `.env`
```env
DATABASE_URL=postgres://postgres.abcdefgh:YOUR-PASSWORD@aws-0-eu-central-1.pooler.supabase.com:5432/postgres?sslmode=require
SUPABASE_URL=https://abcdefgh.supabase.co
SUPABASE_ANON_KEY=eyJhbGciOi...      # از Project Settings → API کپی کنید
```

### ۲.۴ ساختِ جداول
```bash
npm run migrate
```

راهنمای کاملِ اتصالِ احراز هویت (ورود با گوگل از طریقِ Supabase) در
«راهنما-ورود-گوگل.md» آمده است.

### ۲.۵ انتشارِ برنامه روی اینترنت
نسخه‌ی استاتیک (GitHub Pages) فقط صفحات را دارد و سرور ندارد؛ بنابراین برای اینکه
برنامه واقعاً روی اینترنت برای همه کار کند، باید **سرور Node** را هم روی یک میزبان
اجرا کنید و آدرسش را به frontend بدهید:

1. سرور را روی یکی از این‌ها مستقر کنید (همه‌شان با این پروژه کار می‌کنند):
   **Render / Railway / Fly.io / VPS شخصی**
2. متغیرهای `DATABASE_URL`، `JWT_SECRET` و `CORS_ORIGIN` را در تنظیماتِ همان میزبان قرار دهید.
3. frontend را با این متغیر بسازید:
   ```bash
   VITE_API_BASE=https://آدرس-سرور-شما npm run build:demo
   ```
4. پوشه‌ی `dist` را روی GitHub Pages یا هر هاستِ استاتیک منتشر کنید.

## ۳) اگر حتماً MongoDB می‌خواهید

راهکار یک برنامه‌ی حسابداری است و برای ترازِ دقیقِ بدهکار/بستانکار به تراکنشِ
رابطه‌ای (SQL) نیاز دارد. بنابراین MongoDB به‌عنوان پایگاهِ اصلی توصیه نمی‌شود.
اگر با این حال می‌خواهید داده‌ها در Mongo هم باشند، دو مسیرِ عملی وجود دارد:

### مسیرِ الف) Mongo فقط برای بایگانی و گزارش (بدون تغییر در برنامه)
- پایگاهِ اصلی همان PostgreSQL/فایل می‌ماند؛
- یک برنامه‌ی کوچک (یا cron job) هر شب خروجیِ CSV/JSON را در Mongo می‌ریزد:
  ```bash
  # خروجی از داخل برنامه: دکمه‌ی «دریافت نسخه‌ی پشتیبان» در بخشِ سازمان
  mongoimport --uri "mongodb://localhost:27017" --db erp --collection journal \
    --file backup.json --jsonArray
  ```
- مزیت: ریسک صفر برای داده‌های مالی.

### مسیرِ ب) تبدیلِ کامل به Mongo (پیشرفته)
نیازمند نوشتنِ یک لایه‌ی سازگار است که رابطِ `server/database.ts` را پیاده کند
(همان توابع: `listAccounts`, `createJournal`, `listInventory`, …) با درایورِ
`mongodb` و استفاده از **transactionهای چندسنده** که فقط روی replica-set فعال‌اند.
ساختارِ پیشنهادی برای نگاشت:

| جدولِ فعلی           | معادل در Mongo                |
|----------------------|-------------------------------|
| `organizations`      | collection `organizations`    |
| `accounts`           | collection `accounts`         |
| `journal_entries`    | collection `journal_entries`  |
| `journal_lines`      | collection `journal_lines`    |
| `inventory_items`    | collection `inventory_items`  |

و برای هر سندِ حسابداری باید ابتدا `journal_entry` درج شود، سپس خطوط، و در پایان
ترازِ بدهکار/بستانکار بررسی گردد (همان منطقِ فعلی در `server/database.ts`).

> توصیه‌ی ما: برای نسخه‌ی اول از PostgreSQL یا Supabase استفاده کنید. Mongo را بعداً
> و فقط برای بایگانی اضافه کنید.

## ۴) انتقالِ داده‌ها بین حالت‌ها

| از            | به            | روش                                                                 |
|---------------|---------------|---------------------------------------------------------------------|
| فایل → فایل   | کپی           | کپی کردنِ پوشه‌ی `.data` روی دستگاهِ جدید                            |
| فایل → Postgres | خودکار      | مقداردهیِ `DATABASE_URL` و اجرایِ `npm run migrate` سپس import از پنلِ سازمان |
| Postgres → فایل | پشتیبان      | «دریافت نسخه‌ی پشتیبان» در بخشِ سازمان، سپس حذفِ `DATABASE_URL` و «بازگردانی از فایل» |
| Postgres → Postgres | pg_dump  | `pg_dump "$DATABASE_URL" > backup.sql` و `psql "$TARGET" < backup.sql` |

## ۵) خطاهای متداول

| پیام                                        | دلیل و راه‌حل                                                                 |
|---------------------------------------------|-------------------------------------------------------------------------------|
| `DATABASE_URL تنظیم نشده است`               | مقدار در `.env` خالی است یا فایلِ `.env` کنارِ `package.json` نیست.             |
| `password authentication failed`            | رمزِ پایگاه داده اشتباه است؛ از pgAdmin یا پنلِ Supabase دوباره بردارید.        |
| `ECONNREFUSED 127.0.0.1:5432`               | سرویسِ PostgreSQL اجرا نیست (ویندوز: «Services» → postgresql → Start).          |
| `SSL required` / `no encryption`            | به انتهای رشته‌ی اتصال `?sslmode=require` اضافه کنید.                           |
| `prepared statement already exists`         | از Transaction pooler (پورت ۶۵۴۳) استفاده کرده‌اید؛ به Session pooler (۵۴۳۲) بروید. |
| `relation "organizations" does not exist`   | مهاجرت اجرا نشده؛ `npm run migrate` را بزنید.                                   |
| بعد از ری‌استارت داده‌ها نیست (حالت فایلی)  | `DATA_DIR` تغییر کرده یا پوشه‌ی `.data` پاک شده است.                            |

## ۶) امنیت

- `DATABASE_URL` حاوی رمز است؛ فایلِ `.env` در `.gitignore` هست و هرگز در گیت‌هاب
  منتشر نمی‌شود.
- در سرورِ واقعی دسترسیِ شبکه به پورتِ پایگاه داده را فقط برای سرورِ برنامه باز بگذارید.
- هر هفته یک نسخه‌ی پشتیبان بگیرید و آن را خارج از سرور نگه دارید.
